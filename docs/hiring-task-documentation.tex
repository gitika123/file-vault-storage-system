\section{Product overview}
\subsection{What the product is about}
File Vault is a secure personal and team file-management application. Each registered user receives a private vault where they can upload one or many files, organize files into folders, search and filter their own content, inspect metadata, preview supported formats, download files, and manage sharing permissions. The system is designed around explicit ownership: the uploader/owner controls deletion and sharing, while administrators can oversee workspace activity without deleting files owned by other users.

The product also addresses real file-platform concerns. Identical content is stored once through SHA-256 content addressing, user quota usage is measured from logical ownership, storage savings are calculated from deduplicated physical references, and download activity is counted for public files and surfaced in analytics.

\subsection{Primary user journeys}
\begin{itemize}
\item A new user registers, signs in, and receives a private vault with the default quota.
\item A user uploads files through the picker or drag-and-drop. Each file is streamed, validated, hashed, quota-checked, and either stored as a new blob or linked to an existing blob.
\item A user views a file list, opens metadata, moves files into folders, previews supported files, downloads content, and deletes only files they own.
\item A user shares a file or folder directly with another registered user or creates a public link, and can later revoke access.
\item An administrator uploads and shares files, lists all workspace files with uploader details, and views protected usage, download, and deduplication statistics.
\end{itemize}

\section{Core features and implementation}
This section follows the core feature categories from the hiring task and states how each requirement is implemented.

\subsection{File uploads}
\textbf{Requirement.} Support single and multiple file uploads, drag-and-drop upload in the frontend, and content validation against the declared MIME type.

\textbf{Implementation.} The frontend uses a multiple-file input and a global drag/drop guard that prevents browser navigation when files are dropped anywhere in the vault. The upload service streams multipart content with bounded request and per-file limits, calculates SHA-256 during ingestion, checks signatures and format structure against the declared MIME type, and returns a per-file result so a mixed batch reports successes and rejections independently. Forged extensions or mismatched content are rejected before commit.
\shot{Upload and drag-and-drop}{Upload action in its resting state and a capture showing the drop target highlighted while files are dragged over the vault.}

\subsection{File management and sharing}
\textbf{Requirement.} Users can list and view owned files with detailed metadata; organize files into folders; share files and folders publicly or keep them private; optionally share directly with specific users; show public download counters; and allow only the uploader to delete a file.

\textbf{Implementation.} File metadata is owner-scoped and includes uploader identity, logical size, detected and declared MIME types, upload time, blob size, reference count, visibility, and download count. Folders are owner-scoped records with optional parent folders. Files can move between root and folders. Folder cards support open, rename, share, and delete through a context menu, including right-click behavior from the home inventory and folders view.

Public links use cryptographically random tokens whose hashes are persisted. Direct shares persist recipient and permission, inherit folder access for files inside a shared folder, and expose revocation. Private access is the default. Delete handlers enforce ownership, protect other users' files from deletion, and remove physical blobs only when the final logical reference is gone.
\shot{File details and sharing}{File-details view showing uploader, MIME validation, deduplication references, folder movement, public-link copy, direct sharing, and revoke controls.}

\subsection{Search and filtering}
\textbf{Requirement.} Search by filename; filter by MIME type, size range, date range, tags, and uploader name; combine filters; optimize queries for scale.

\textbf{Implementation.} The list endpoint accepts parameterized filters and bounded cursor pagination. Filename search uses PostgreSQL text search/index support, while owner, uploader, folder, upload date, MIME, size, and tag predicates are combined in one query. The frontend presents the requested categories: selectable MIME type, minimum and maximum bytes, uploaded-after and uploaded-before dates, tag, uploader name, plus filename search. The date fields represent the inclusive upload timestamp range; the backend normalizes them to UTC boundaries and rejects inverted ranges. Search-plan evidence is in \code{docs/performance/search-plan.md}.
\shot{Search and filtering}{File inventory with filename search and MIME, size, date, tag, and uploader filters applied together.}

\subsection{Rate limiting and quotas}
\textbf{Requirement.} Enforce per-user API rate limits with a configurable default of 2 calls per second, configurable per-user storage quota with a default of 10 MB, and proper error codes/messages.

\textbf{Implementation.} The limiter is keyed by authenticated user identity and configured through \code{API\_RATE\_PER\_SECOND} and \code{API\_RATE\_BURST}. The quota is configured through \code{USER\_QUOTA\_BYTES}, defaulting to 10 MiB (10\,485\,760 bytes). Uploads make the quota decision transactionally against logical owned bytes, including duplicate uploads without double-charging physical storage. Exceeded limits return structured errors, including HTTP 429 for rate limiting and HTTP 413 with a quota-specific code for storage overflow. Redis-backed limiter state is used when \code{REDIS\_URL} is configured for multiple replicas.

\subsection{Storage statistics}
\textbf{Requirement.} Display total deduplicated storage used, original usage without deduplication, and savings in bytes and percentage.

\textbf{Implementation.} Original usage is the sum of active logical file sizes owned by the user. Deduplicated usage sums distinct referenced blob sizes for that user. Savings bytes equal original usage minus deduplicated usage, and savings percentage is savings divided by original usage, with a zero-safe calculation. The user dashboard displays summary cards and visualizations; administrators see workspace-wide metrics, download totals, user counts, file counts, and visual analytics.
\shot{Storage statistics}{User storage cards and visual analytics showing original versus deduplicated usage, savings, and quota consumption.}

\subsection{Admin panel}
\textbf{Requirement.} Admins can upload files and share them with other users; the admin panel lists all files with uploader details; admins can view download counts and usage statistics.

\textbf{Implementation.} Administrator routes are protected by RBAC. The administrator screen separates an admin home for upload/share actions, an all-files inventory with uploader name/email, MIME, size, date, and download count, and a Statistics tab with workspace usage and Recharts visualizations. Administrators can inspect and share files but cannot delete files owned by another user. Admin and user statistics use the same logical/physical semantics, scoped to their respective views.

\section{Product orchestration and infrastructure}
\subsection{Runtime orchestration}
Docker Compose orchestrates PostgreSQL for relational state, Redis for shared limit state, the Go API for business logic, and Nginx serving the React build while proxying API/public-content requests. Health checks ensure the API starts after dependencies are ready. The API runs idempotent seed logic only when runtime seed variables are supplied; secrets and passwords are not stored in source control.

\subsection{Data and storage orchestration}
The database owns logical metadata and relationships. The blob adapter owns physical content. A file row references a content-addressed blob by digest; multiple file rows can reference one blob. Reference counts are updated transactionally, and deletion removes the physical object only after the final reference disappears. Production uses the S3-compatible adapter so multiple API replicas share the content plane.

\subsection{Security orchestration}
Authentication uses Argon2id password hashes, database-backed sessions, HttpOnly cookies, CSRF tokens, and explicit owner/admin policy checks. Public share tokens are random and persisted only as hashes. Private, direct-share, and public-content paths are authorized separately. The API returns structured error codes rather than exposing implementation details.

\subsection{Deployment orchestration}
Raw Kubernetes manifests are in \code{k8s/}; the Helm chart is in \code{helm/balkanid/}. They include API/frontend Deployments and Services, PostgreSQL, Ingress, ConfigMap, Secret template, probes, service account, and PVCs. A real cloud launch should use managed PostgreSQL, managed Redis/Key Value, shared object storage, TLS, external secrets, backups, and observability.

\section{Bonus points implemented}
\begin{itemize}
\item \textbf{Folder organization:} owner-scoped/nested folders, file movement, rename/delete rules, context menus, public folder links, and direct folder sharing with inherited access.
\item \textbf{Kubernetes:} Deployments, Services, Ingress, ConfigMap, Secret template, probes, PostgreSQL resources, and PVCs under \code{k8s/}.
\item \textbf{Helm:} reusable chart under \code{helm/balkanid/}; lint and template validation were performed.
\item \textbf{CI/CD:} GitHub Actions runs formatting, \code{go vet}, Go tests, frontend lint/build, Playwright UAT, and Linux Docker builds. GHCR publication is configured for the repository branch using the workflow token.
\item \textbf{Kubernetes deployment workflow:} manual workflow dispatch can apply manifests and roll out published images when \code{KUBE\_CONFIG\_B64} is configured.
\item \textbf{UAT automation:} Playwright covers authentication, upload, MIME rejection, deduplication, search, folders, sharing, previews/downloads, admin authorization, drag-and-drop, and navigation.
\item \textbf{Real-time activity:} authorized download events are published over SSE and consumed by user/admin views to refresh counters and statistics.
\item \textbf{Preview and public statistics:} PDF/image and safe media/text preview paths, public download counters, and inline file-detail preview behavior.
\item \textbf{Scale evidence:} cursor pagination, parameterized queries, search indexes, documented query-plan evidence, Redis limiter support, and S3-compatible storage adapter.
\end{itemize}

\section{AI-assisted engineering methodology}
AI was used as a productivity aid for requirement decomposition, implementation proposals, test-case generation, security review, UI review, and documentation drafting. The methodology remained human-directed and evidence-based:
\begin{enumerate}\item Convert the brief into dependency-ordered issues and acceptance criteria.\item Give the assistant one bounded issue at a time with repository and security constraints.\item Request the smallest reviewable change in the correct module.\item Inspect the diff and review authorization, transactions, error handling, and data exposure.\item Add focused tests for success, failure, authorization, boundaries, and concurrency.\item Re-run deterministic checks and update documentation only when runtime evidence supports the claim.\end{enumerate}
Reusable prompt patterns and the complete methodology are recorded in \code{docs/ai-prompts.md} and \code{docs/ai-methodology.md}. No credentials, tokens, private files, or secret values are included in source control.
